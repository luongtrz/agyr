# Parallel agy runs (max 20 at a time)

Read this when the user wants several independent tasks done at once.

**Limit:** up to **20** concurrent agy runs (user rule 2026-10-12, raised from 12 and earlier from 6). The reason is that agy and `agy-task` run no tests, so parallel agy runs do not load the machine; the load comes from YOUR verification afterwards, so run those one at a time (a worktree at a time), never several suites at once. Count live runs before launching more, both implement (`agy-task`) and read-only (`agy-run`): `pgrep -fc '^bash .*agy-(task run --name|run --prompt)'`. Other sessions' runs on the host count too.

**Never resume the same Claude session in a second terminal while the first is alive.** (2026-09-25: a `claude --resume` terminal committed/pushed a fix, removed a worktree and relaunched an audit while the other terminal drove the same task; the host also lagged with 3 agy runs + tsc/vitest/vite.) Before launching check `pgrep -af "agy -p"`; if `ps` shows another `claude --resume <this-session-id>`, stop and tell the user first.

**Rules**
- **One background tool call per task (NEVER bundle into a wrapper script or `wait` loop):** launch each `agy-task run` or `agy-run` as its own separate background command tool call (with the task name in `toolSummary` / description). Never write a batch launcher (`launch.sh`, `queue.sh`, or `for pid in "${pids[@]}"; do wait "$pid"; done`) that spawns multiple `agy-task` processes inside a single command. A single bundled command hides individual task progress in the UI and delays your wakeup notification until the slowest task in the entire batch finishes. With separate background tool calls, the system notifies you as soon as each individual task finishes so you can review, test, and integrate it immediately.
- **Implement tasks: one git worktree per run** — `agy-task run --name <task> --base <same-sha> …` creates and prepares it (setup + copied generated files from the repo config), so give each parallel run its own `--name` and the same `--base`. Never let two runs write the same worktree — even disjoint files collide in concurrent vitest/tsc runs and make the diff impossible to attribute.
- **Splitting a multi-part feature across parallel runs:** split by non-overlapping `--scope` paths (e.g. DB/repo layer, service layer, server adapter/handler) and pin the exact exported names, function signatures, types and sentinel errors that both sides rely on in every task file (the sibling's code does not exist in that worktree yet). For backend/Go-only tasks where `SETUP_CMDS` (e.g. `pnpm install` + `api:gen`) is unneeded, pass `--no-setup` to save time. Note that `COPY_FILES` in `agy-task` copies from the MAIN checkout: if your current branch is in a linked worktree with new routes not on the main checkout, copy `routeTree.gen.ts` from your branch worktree into the agy worktree before running `tsc`.
- Read-only review runs can share the main checkout (they must not write).
- Each parallel run burns its own quota; a 429 in one run doesn't stop the others — check every run's `result` event. All runs share one account pool (see `quota-auth.md`).
- If the tasks touch the same files heavily, run them sequentially in one worktree instead; parallelism pays only when the conflict surface is small.

**Integrate as each task finishes, one run at a time:** as each background task sends its completion notification, review its worktree diff and run its targeted tests yourself (one worktree at a time), then commit/integrate it before or while waiting on the remaining running tasks. Tasks touching the same files (validator + its test, same dialog) usually conflict at the ends of test files — resolve by keeping both sides, then re-run the full verify on the integrated branch before fast-forwarding the MR branch.

**More than 20 tasks:** launch up to 20 separate background tool calls first; each time one finishes and wakes you up, review/integrate it and launch the next unstarted task as its own background tool call. Never use a background `queue.sh` or `wait` loop.
